Storage is a period average, not a current audio inventory. No evidence of an exhausted Supabase quota at the time of inspection.

Code inspection found student state polling every 3 seconds and teacher refresh every 4 seconds. Teacher refresh calls BOTH classes and dashboard. Thirty continuously polling students plus one teacher would therefore generate about 37,800 automatic requests/hour before network timing and browser throttling, not the previously estimated 36,900. This is a calculation, not observed billing.

Minimal change: pause automatic polling in hidden tabs; resume immediately when visible; wait until each automatic refresh settles before scheduling the next. Student active/unanswered or processing: 3 seconds; waiting/completed/failed: 10 seconds; ended: 30 seconds unless processing. Teacher active or processing: 4 seconds; otherwise: 30 seconds. Requests caused by explicit user actions still run normally. A request already running when a page hides is allowed to finish.

For 30 visible waiting/completed students, the nominal student polling rate falls from 36,000 to 10,800 requests/hour (70% reduction in this state only). Teacher active rate stays unchanged; real savings depend on page visibility, state and network latency. New questions can take up to approximately 10 seconds plus request latency to reach waiting students. An ended classroom reopened by the teacher can take up to 30 seconds plus request latency to be detected.

No database migration, new scheduler, Realtime dependency, OpenRouter integration, Gemini load test or billing change in this patch.

The teacher rescue action is now labeled “Process unfinished responses / 補處理未完成作答”, with an explanation that only failed or >90-second processing recordings are retried. This reuses the existing retry endpoint and four-concurrent-start helper; it adds no scheduled rescue jobs. Discarding an old local recording now triggers an immediate parent render instead of waiting for polling.
